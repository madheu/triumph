# Triumph 代码审查流程

> 适用对象：你自己（不写代码）、以及任何协助改代码的 agent/会话。
> 目的：让"改动"可控可回退，避免改坏线上功能。
> 配套：`维护手册.md`（怎么部署/回滚）、`agent协作工作流.md`（谁改什么）。

---

## 0. 铁律（三条，违反任何一条都算流程失败）

1. **先备份，再动手**：任何改动前，`git` 先提交一次（部署前快照）。
2. **先测试，再部署**：`npm test` 必须 `fail 0` 才允许上线。
3. **改动要有"影响面"概念**：越靠近"全站"的改动（Worker、首页、密钥），审查越严格。

---

## 1. 改动前要看什么（Pre-change Checklist）

### 1.1 先读这些（30 秒定位现状）
- [ ] `README-deploy.md` —— 部署方式、site/ 与 functions/ 的关系
- [ ] `docs/维护手册.md` 第 2 节 —— 目录里哪些文件能碰
- [ ] `docs/agent协作工作流.md` —— 本次改动该由谁做、有没有在做的会话
- [ ] `待办标注.md` —— 确认不是已标注的 mock/占位项（避免重复踩坑）

### 1.2 判断改动类型（决定审查深度）

| 类型 | 例子 | 审查深度 |
|---|---|---|
| 🟢 文案/样式 | 改一段文字、改颜色、改间距 | 轻：肉眼 + 截图确认 |
| 🟡 页面功能 | 改答题页逻辑、加一个按钮 | 中：跑测试 + 本地预览 |
| 🔴 后端接口 | 改 `worker-src/` 的账号/题库/路由 | 重：全量测试 + 逐条 review |
| 🔴 密钥/配置 | 改 `.dev.vars`、线上 Secret | 重：确认无泄露、可回滚 |
| 🔴 数据/迁移 | 改题库 JSON、KV→D1 迁移 | 重：备份 + 灰度 + 回滚预案 |

### 1.3 改动前必答的三个问题
1. **要解决什么问题？**（说人话，比如"用户收不到验证码邮件"）
2. **动哪些文件？**（列具体路径）
3. **如果改坏了，怎么回来？**（回滚方案，见第 4 节）

> 如果三个问题答不上来 → **不许动手**，先回去想清楚。

## 2. 改动中如何避免破坏现有功能（During-change）

### 2.1 最小改动原则
- 只改"要解决的问题"相关的文件，**不顺手重构、不顺手格式化无关代码**
- 一个改动 = 一个目的。想做的第二件事，开第二个改动

### 2.2 不破坏测试基线
- 改之前：`npm test` → 记住当前 `pass` 数（现在应为 46）
- 改之后：`npm test` → `pass` 数**不能变少**；变少 = 破坏了某功能，必须修
- 如果测试本身需要更新（比如故意改了行为）→ 必须**同时**更新测试并在审查中说明理由

### 2.3 保护导出契约（worker 特有，重要）
`test/agentic.test.mjs` 会从 `site/_worker.js` 直接导入这些名字：
```
parseAccept / negotiatePageVariant / varyWithAccept / MD_ROUTES / openApiSpec / specToYaml
```
- 改 `worker-src/` 时**绝不能删掉或改名**这些导出，否则测试直接崩
- 新增功能：只**增加**路由/函数，不删旧的

### 2.4 渐进式验证（每改一步都验证，不要攒到最后）
- 改文件 → 跑一次 `npm test`（快，几秒）→ 通过再继续下一处
- 本地 `wrangler pages dev` 打开页面点一点，确认交互正常

### 2.5 代码风格约定（保持一致性）
- `site/` 与 `worker-src/` 全部用 ES Module（`import`/`export`），不要混用 CommonJS（`require`）
- 新文件放 `worker-src/` 并按功能命名（如 `billing.mjs`），入口统一在 `worker.mjs` 挂路由
- 中文注释写"为什么"，不写"做了什么"（代码本身能看出做了什么）
- 字符串/文本用英文（面向美国用户），注释/文档用中文

## 3. 改动后如何验证（Post-change Checklist）

### 3.1 自动验证（必做）
```powershell
npm test
```
- [ ] 通过（`fail 0`）
- [ ] 若测试数变了（加了新测试）→ 注明

### 3.2 本地验证（页面改动必做）
```powershell
wrangler pages dev site --port 8799 --binding JWT_SECRET=dev --compatibility-date=2026-08-18
```
- [ ] 打开 http://localhost:8799 走一遍受影响的功能
- [ ] 手机宽度看一眼（F12 → 设备模拟）

### 3.3 线上验证（部署后必做）
```powershell
curl.exe -s https://trytriumph.de5.net/api/v1/health
```
- [ ] 返回 `ok:true`
- [ ] 强制刷新主站（Ctrl+F5）检查改动生效
- [ ] 检查 Cloudflare 控制台 Logs 无新增报错

### 3.4 数据类改动验证
- [ ] 备份原数据文件
- [ ] 新数据跑通 `npm test`（题库测试会校验数量/结构）
- [ ] 线上抽查 3-5 条真实数据

## 4. 必须写回滚方案的情形（⚠️ 触发即写）

以下任一情况，改动**开始前**就必须写清楚回滚方案（一行即可，但要具体）：

1. 🔴 改了 `worker-src/` 的**路由/认证/数据存储**逻辑
2. 🔴 改了 `.dev.vars` 或线上 Secrets（密钥）
3. 🔴 迁移了数据（KV → D1、题库换源）
4. 🔴 改了部署流程（`deploy.ps1`、构建脚本）
5. 🟡 删除了任何线上文件或旧功能

**回滚方案模板**（写进改动说明里）：
```markdown
## 回滚方案
- 现象:（出什么问题算需要回滚）
- 步骤:（具体命令/操作，如: 把 backups\xxx 复制回 site\ 后运行 .\deploy.ps1）
- 参考: 维护手册.md 第 9 节
```

---

## 5. 必须人工确认的情形（❌ agent 不能自己决定）

以下情况 agent 必须停下、把方案交给你确认，**不得自行执行**：

1. **任何涉及钱的改动**：支付密钥、定价、退款流程、Creem 配置
2. **任何涉及用户数据的大规模操作**：批量改用户状态、清空数据、迁移用户表
3. **删除功能/页面**：哪怕看起来"没用了"（可能有人正用着）
4. **改公开接口的响应格式**：其他程序（MCP/开发者 API）依赖它
5. **发布动作本身**：`deploy.ps1` 跑不跑、什么时候跑，由你拍板（agent 可以准备好，不主动部署线上）
6. **密钥轮换**：涉及 Cloudflare token 重建，必须你本人在控制台操作
7. **加新依赖**：往 `package.json` 加新工具包，需说明为什么非加不可

---

## 6. 如何记录审查结论

每次改动（无论大小）在 **`docs/审查记录.md`** 末尾追加一条，格式：

```markdown
## 2026-08-23 修复验证码邮件发不出去
- 改动人: agent (会话 xxx)
- 改动文件: worker-src/accounts.mjs, site/_worker.js(由构建生成)
- 问题: 用户收不到验证码，原因是 Resend 密钥过期
- 方案: 更新线上 Secret + 补一个测试
- 验证: npm test 46/46 ✅；线上 curl health ok
- 回滚方案: 无（配置类改动，密钥可随时换回）
- 结论: ✅ 通过 / ⚠️ 有条件通过（条件: xxx）/ ❌ 打回（原因: xxx）
```

**审查结论三档**：
- ✅ **通过**：测试绿 + 影响面核对完 + 无遗留风险
- ⚠️ **有条件通过**：功能 OK 但留下待办（写进 `待办标注.md`），可先上线
- ❌ **打回**：测试挂了 / 影响面未说明 / 没有回滚方案 / 越权改动了第 5 节内容

**审查节奏**：不追求一次大审查，改为**每次改动小审查**（几分钟），比攒一个月审一次可靠得多。
