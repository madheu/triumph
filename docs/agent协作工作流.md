# VS Code + agent 协作工作流

> 适用对象：你自己（非技术）、以及帮你改代码的 agent 会话。
> 目标：VS Code 做"看和改"的场所，agent 做"分析和写"的劳力，分工明确、互不覆盖。
> 配套：`维护手册.md`（部署/回滚）、`代码审查流程.md`（怎么验证改动）。

---

## 1. 分工总览

| 事情 | 谁负责 | 工具 |
|---|---|---|
| 看代码、看文件、确认改动内容 | **你**（用眼睛） | VS Code 资源管理器 + 打开文件 |
| 写代码、改文件、跑测试、打包构建 | **agent** | agent 自己的工具 |
| 跑 `npm test`、`deploy.ps1` 部署 | **agent 可以准备和验证，最终执行部署由你确认** | agent / 你 均可 |
| 配置密钥（Cloudflare 控制台） | **只有你** | 浏览器控制台 |
| 判断"要不要做 / 要不要上线 / 花多少钱" | **你** | — |
| 记录每轮做了什么 | **agent** | `docs/会话记录.md` |

**核心原则一句话**：agent 是"手"，你是"脑"。agent 提供方案和结果，你拍板。

---

## 2. 你（人工）在 VS Code 里负责什么

1. **看**：用左侧"资源管理器"浏览项目结构（第 2 节维护手册有目录图）
2. **验证**：让 agent 改完后，你在 VS Code 里打开改动过的文件，**肉眼看一遍**有没有不对劲（比如中文变成乱码、格式乱了）
3. **跑部署**：在 VS Code 的终端（Terminal）里输入 `.\deploy.ps1`（如果 agent 没权限/你没让 agent 跑）
4. **看报错**：终端里红色文字就是报错，截图或复制给 agent
5. **查日志**：线上问题去 Cloudflare 控制台看（维护手册第 6 节有步骤）

> 你不需要会写代码。你只需要：会打开文件、会复制粘贴、会截屏、会跑一条命令。

**VS Code 三个常用操作**（如果没接触过）：
- 打开项目：VS Code → 文件 → 打开文件夹 → 选 `E:\Triumph\praxis-5001`
- 打开终端：顶部菜单 终端 → 新建终端（快捷键 `` Ctrl+` ``）
- 在终端里运行命令：直接输入命令回车（如 `npm test`）

## 3. agent 负责什么

agent（如 Hermes/DeepSeek 等 AI 编程助手）负责：

1. **读代码找原因**：你说"用户收不到验证码"，它去翻 `worker-src/accounts.mjs`、查配置，定位问题
2. **写代码**：按你的指示和 `代码审查流程.md` 修改文件
3. **跑测试**：`npm test`，把结果汇报给你
4. **跑构建**：`npm run build:worker`（把 worker-src 打包）
5. **跑本地预览**：`wrangler pages dev`（如果它能在后台跑）
6. **写文档**：把改动记录进 `docs/会话记录.md` 和 `docs/审查记录.md`
7. **给方案**：遇到大改动，先给"方案 + 影响面 + 回滚方式"，等你确认再动手（见第 5 节）

**agent 不负责**（红线）：
- ❌ 不主动部署线上（除非你明确说"部署"）
- ❌ 不碰密钥（.dev.vars 值、线上 Secret）
- ❌ 不删功能、不改接口格式、不碰钱的逻辑（见代码审查流程第 5 节）
- ❌ 不做超出你确认范围的"顺手优化"

## 4. 哪些文件可以直接改，哪些必须先出方案

### ✅ 可以直接改（低风险，agent 改完跑测试即可）
| 文件/目录 | 说明 |
|---|---|
| `site/*.html` 的文案、样式、页面结构 | 改完本地预览确认 |
| `site/css/` | 样式 |
| `site/md/*.md` | 文章内容（Markdown） |
| `site/js/*.js`（除 `_worker.js`） | 前端交互逻辑 |
| `worker-src/` 内**新增**模块（如新建 `billing.mjs`） | 新功能，不碰现有路由 |
| `docs/` 下的文档 | 维护记录 |

### ⚠️ 必须先出方案再动手（中风险，agent 给方案 → 你确认 → 才改）
| 文件/目录 | 说明 |
|---|---|
| `worker-src/accounts.mjs` / `bank.mjs` / `worker.mjs` 等**现有**模块 | 改现有逻辑要说明影响面 |
| `site/data/questions-api.json` | 题库数据，改前备份 |
| `deploy.ps1` / `build-worker.mjs` / `package.json` | 构建部署流程 |
| `wrangler.toml` | Cloudflare 配置 |

### 🔴 你亲自做或明确批准后 agent 才能碰
| 事项 | 说明 |
|---|---|
| `.dev.vars` / 线上 Secrets | 密钥，只能你配置 |
| Creem 支付配置 | 审核通过后你配密钥 |
| Cloudflare 控制台任何操作 | 登录、删 token、改 zone 设置 |
| 删除任何线上功能/页面 | 先问"有人用吗" |
| 迁移用户数据 | 涉及真实用户 |

## 5. 如何避免多个会话互相覆盖（重要！）

场景：你开了一个 agent 会话让它改 A，又开了另一个让它改 B，两个会话同时写 `site/` —— 后写的会覆盖先写的，可能互相毁掉。

### 5.1 会话锁机制（简单有效）
在项目根目录放一个 `docs/会话锁.md`，**一个会话开工前先写**：

```markdown
# 会话锁
- 持有会话: agent-会话A
- 锁住的范围: worker-src/ 和 site/data/
- 开始时间: 2026-08-23 14:00
- 预计结束: 2026-08-23 15:00
- 联系方式: 结束后立即清空本文件
```

规则：
- 一个会话想改某个范围 → 先读 `会话锁.md`，**若该范围被锁 → 不要动，等解锁**
- 改完 → 清空文件（或写"无会话在改"）
- 如果锁挂了（会话死了没解锁）→ 你手动删掉锁文件，给新会话用

### 5.2 范围隔离（比锁更本质）
- **让不同会话负责不同目录**：会话 A 只改 `worker-src/`，会话 B 只改 `site/` 的页面
- **同一文件只允许一个会话碰**：需要碰同一文件时，一个改完提交后再让另一个开始
- agent 每次动手前，**先 `git status` 看有没有未提交的改动**（说明别人改过，先汇报）

### 5.3 git 兜底
- 每次会话开始：`git add -A; git commit -m "会话开始前快照"`
- 每次会话结束：`git add -A; git commit -m "会话结束：做了什么"`
- 万一覆盖了：`git log` 找历史版本 → `git checkout <版本号> -- <文件>` 恢复
- 不会 git 也没关系：把这条命令复制给 agent 让它执行

### 5.4 沟通习惯
- 一个会话只接**一个任务**，做完汇报再开下一个
- 任务描述里写清楚：改什么文件、不改什么文件、验证方式
- 任何"我顺手改了一下 XX"都是**禁止**的——不顺手改

## 6. 如何保持文档和代码同步

原则：**改动代码 → 同步更新文档**，否则文档会骗人（这个项目已踩过坑：`triumph/` 文件夹还留着旧稿）。

### 6.1 每次改代码后，agent 必须检查并更新（如果涉及）：
| 代码改动 | 要更新的文档 |
|---|---|
| 新增/删除接口 | `README-deploy.md` 的路由表 + `site/openapi.json` |
| 新增/删除页面 | `维护手册.md` 目录结构节 |
| 改环境变量 | `维护手册.md` 环境变量节 |
| 改部署流程 | `README-deploy.md` + `维护手册.md` 构建部署节 |
| 改数据格式 | `维护手册.md` 数据接入节 + 相关 .md |
| 改功能/加功能 | `待办标注.md`（把完成项划掉/更新状态） |
| 修了 bug | `docs/审查记录.md` 追加一条 |

### 6.2 文档更新 checklist（agent 收尾时自查）
- [ ] `docs/审查记录.md` 追加了本次改动
- [ ] `docs/会话记录.md` 追加了本次会话做了什么
- [ ] `docs/会话锁.md` 已清空
- [ ] 涉及接口/页面/密钥 → 对应文档已同步
- [ ] 有新"没做完的事" → 写进 `待办标注.md`

### 6.3 文档"体检"频率
- 每完成一个里程碑（如后台管理上线）→ 全量检查一遍文档一致性
- 至少每月一次：读 `维护手册.md`，看哪些写的不符合现状，让 agent 更新

## 7. 一次典型协作流程（照着做）

1. **你**：在 VS Code 终端 `git add -A; git commit -m "开始前快照"`（或让 agent 做）
2. **你**：告诉 agent 任务："用户注册后收不到验证码邮件，帮我查一下"
3. **agent**：先读 `docs/会话锁.md` 确认没冲突 → 分析 `worker-src/accounts.mjs` → 给出原因和方案
4. **你**：确认方案 → agent 动手改
5. **agent**：改完跑 `npm test`（46/46 通过）→ 汇报改动文件和结果
6. **你**：VS Code 里打开改动文件肉眼看一遍 → 确认没问题
7. **你**：决定是否部署 → 同意后 agent 跑 `.\deploy.ps1`（或你自己跑）
8. **agent**：部署后跑线上验证 curl → 更新 `docs/审查记录.md` + `docs/会话记录.md` → 清空会话锁
9. **你**：手机/浏览器强制刷新确认线上生效

## 8. 给 agent 的标准任务模板（复制即用）

```markdown
任务:（一句话说清楚要做什么）
背景:（为什么做 / 出现了什么问题）
范围:
  可以改:（列出具体文件/目录）
  不许改:（列出文件/目录）
验证方式:（跑什么测试 / 怎么确认成功）
涉及文档:（是否要更新 docs/ 下哪些文件）
其他约束:（比如"不要碰密钥""不要部署线上"）
```

**示例**：
```markdown
任务: 在 worker-src 里新增一个健康检查接口 /api/admin/ping
背景: 后台管理需要探活接口
范围:
  可以改: worker-src/worker.mjs（挂路由）、worker-src/（新增 admin.mjs）
  不许改: accounts.mjs、bank.mjs、site/ 下任何文件
验证方式: npm test 保持 46/46 通过 + 新增一条针对该接口的测试
涉及文档: README-deploy.md 路由表
其他约束: 不部署线上
```
