## 二、P0 — 六个让数据不可用的缺陷

### 1. `elapsed_ms` 恒为 0（106/106，且全表零 NULL）

`events.mjs` 里 `Number(e.elapsed_ms)`，而 `Number(null) === 0`。
于是"调用方没提供耗时"被写成了 0，**「未知」和「0ms 秒答」在数据里无法区分**，
识别乱点的能力直接归零。

→ 先挡缺失值再校验范围。实测 `question_answer` 的 106 条全部是 0、无一条 NULL，
完全印证。

### 2. `result_view` 触发率 12.5%（2 / 16）

`observeOnce` 写死 `threshold: 0.5`。IntersectionObserver 的 ratio 是
「可见面积 / 元素总面积」——**元素一旦高于视口，ratio 上限就只有
「视口高 / 元素高」**。结果页 `.report` 轻松超过 2000px，在 800px 视口下
上限约 0.4，**永远达不到 0.5**，事件等于没埋。

→ 阈值改为 `min(0.5, 视口高 / 元素高)`，下限 0.05。矮元素仍用 0.5，不因自适应而放松。

### 3. `return_visit` 语义与字典不符

字典 §2 定义是「距上次访问 > 24h 且本地有历史结果」；
实现是按 **session 轮换（30 分钟）**判定。
实测同一访客的 `span_hours` 出现 0 和 1 —— 1 小时内报了两次。

→ 新增 `ld_last_visit` 时间戳，按 24h 显式比较，并补上字典要求的
`days_since_last` / `has_saved_result` 两个属性（存 `extra_json`）。

### 4. `correct` / `question_id` 全为 NULL（106/106）

原实现在点选项后 `setTimeout(..., 80)` 读 `button.opt.correct`。
但 React 的渲染条件是 `answered && selected !== null`，
`.correct` 类**只在 reveal 之后才存在** —— 80ms 时读到的是 null。

> 补充：这里推翻了我最初的一个猜测。原本怀疑是 React 异步渲染导致 80ms 不够，
> 但读 React 源码确认点击后 `setSelected` + `setAnswered` 在同一次状态更新里，
> React 18 的离散事件会同步 flush，80ms 足够。真正的原因是**读取时机早于
> reveal，而不是晚于渲染**。

→ 判定改挂到「Next question / See my results」按钮的**捕获阶段**：
该按钮 `disabled={!answered}`，**能点到就说明已经 reveal**，DOM 里必然带 `.correct`。
同时捕获阶段 React 尚未处理本次点击，DOM 仍是当前这道题。

### 5. `content_domain` 存的是 subtest code，不是领域名

字典 §3.2 要求领域名（如 `Earth Science`），实际存的是 `"5004"`。
月底「哪个领域最常成为最弱项」的分析会因此得出错误结论。

→ 改为按题干反查题库取 `category`。题库 969 题、**题干 969/969 唯一**，反查可靠。
顺带补上 `question_id`（题库 `id`）。

### 6. `test_start` 被重复埋点，导致漏斗串联断裂

`diagnostic.html` 的内联脚本和 `signup-hook.js` **各发一次** `test_start`，
各生成一个 `attempt_id`。生产库可见同一访客同一秒两条：

```
01:32:31  test_start  attempt=89dfe6e1...
01:32:31  test_start  attempt=c6b9040a...
```

后续 `question_answer` 全归到前者、`test_complete` 两个都出现 ——
**漏斗按 `attempt_id` 串联直接失效**。

→ 统一由内联脚本负责（它拿得到 `score_pct`，数据更完整），
`signup-hook.js` 不再重复发，改用 `L._state().attemptId` 取同一个 id。

## 三、P1 — 补上缺口

### 付费漏斗（3 个新事件）

原 12 个事件**止于 `signup_success`**，注册之后整段是黑的。
转化优化里的付费点（P1-4）、价格锚点（P1-5）、解锁态摘要（P0-3）做完，
**没有任何办法判断效果**。

新增并打通三处（tracking.js / events.mjs / D1 CHECK 必须同步，漏一处事件被静默丢弃）：

| 事件 | 自有表 | GA4 | 触发时机 |
| --- | --- | --- | --- |
| `upgrade_view` | ✔ | `view_promotion` | 升级页加载 |
| `checkout_start` | ✔ | `begin_checkout` | 点「Upgrade to Pro」**且已登录** |
| `purchase_success` | ✔ | `purchase` | 以 `?pro=1` 回跳 |

`purchase_success` 的判定刻意不用"用户自称付过款"：`?pro=1` 由升级页自身的
轮询脚本在 `/api/me` 确认 `plan=pro` 之后才附加，等价于**后端已确认收款**。

GA4 侧带 `value: 15` / `currency: 'usd'` —— 没有 value 的 `purchase`
在 Ads 和默认报表里基本读不出东西。

### 注册路径接入（`login.html`）

新增 `site/js/login-tracking.js`：不碰压缩过的流程脚本，
用「监听可观察的 DOM 事件 + 包装 `TriumphAuth` 的公开方法」两种手段接线。

- `signup_start` — 注册/验证流程提交时，或主动点「Sign up」切换过去时
- `signup_success` — 包装 `register` / `verify`，在 Promise resolve 时发出
- Google 回跳落地也计入（`magic_link` / `google` 分开标记）

### 首页接入（`index.html`）

首页本身不在五段漏斗里，加载埋点只为一件关键的事：
`traffic_source` 在**首次访问**时固化。实测 21 个访客的首站全是
`diagnostic` / `8006`，**没有一个从首页进入** —— 说明目前这个风险还没兑现，
但一旦有从首页进来的流量，这批人的来源会被误判为 `direct`
（判定时 referrer 已是站内地址），所以现在补上。

### 顺带修正 GA4 的 `sign_up` 口径

`auth.js` 里 GA4 的 `sign_up` 原本在「**提交注册**」时就发（逗号表达式放在
`need_verify` 判断之前），**未验证也计入**。已移到验证真正完成时，
与自有表的 `signup_success` 同一时刻发出，两者一一对应。

### 口径统一

`signup_method` 由 `magic_code` 统一为字典口径 `email_code`
（它同时也是 `login.html` 的 密码+验证码 路径；`signup_success` 此前恒为 0，无历史包袱）。

## 八、关于"数据能回答什么"

修完之后，之前答不出的问题现在有数据了：

- **「没人愿意做测试」还是「做完了没看见注册入口」** → `test_view → test_start` 与
  `test_complete → signup_prompt_view` 两段分开看
- **注册入口是不是埋太深** → `signup_prompt_view` 现在有了。此前恒为 0，
  而 `.paywall`（注册卡片所在位置）在结果页靠下 —— 用户做完题看到顶部成绩就走，
  根本没滚到那里。**这很可能就是"注册转化率太低"的真实机制**：
  不是文案问题，是入口位置问题
- **付费点改动有没有用** → `upgrade_view → checkout_start → purchase_success`
- **哪个领域最该扩题** → `question_answer.content_domain` 现在存的是真实领域名

但仍要注意口径：**`orders` / `subscriptions` 才是收款的权威记录**，
`purchase_success` 是前端观测。两者不一致时以 orders 为准。
