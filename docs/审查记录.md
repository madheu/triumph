## 2026-09-11 修复「$9.99 报告付完钱落 404」
- 改动人: agent（切 live / 报告阶梯会话）
- 改动文件: `worker-src/billing.mjs`（`hReportCheckout` 的 `success_url`）、`test/p1-billing.test.mjs`
- 问题: 一次性报告的支付回跳写成 `https://learndiag.com/report.html?purchase=done`，
  而 **`site/report.html` 根本不存在**（线上 404）。用户付完 $9.99 会落在 404，拿不到报告。
- 方案: 改为 `/diagnostic?purchase=done` —— `site/js/report.js` 设计上就在诊断页运行
  （它查 `#root main` / `.paywall` / `.intro`，并处理 `purchase=done`）。
  订阅侧 `/upgrade.html?checkout=done` 实测 308 → `/upgrade?checkout=done`，**query 保留、功能正常，不动**。
- 验证: 新增守卫 `test/p1-billing.test.mjs` test 108 —— 从 `billing.mjs` 抽出所有 `success_url` 字面量，
  映射到 `site/` 下文件，**不存在就红**；并加反例断言禁止 `'/report.html'` 回归。已实测能抓到该 bug。
- 回滚方案: 改回旧 URL（但旧 URL 是坏的，实际等于不回滚）
- 结论: ✅ 通过。**教训：改支付链路上的任何 URL 都要先 `curl` 验一遍，不能凭设计意图假设它存在。**

## 2026-09-11 修复首页丢失 `</script>` 导致埋点静默失效
- 改动人: agent
- 改动文件: `site/index.html`、`test/agentic.test.mjs`
- 问题: `git diff` 里出现孤零零一行 `-</script>` —— 另一会话注入埋点时删了闭合标签未补回（10 开 9 闭）。
  浏览器在 `<script>` 内把内容当**原始文本**读到第一个 `</script>` 为止，所以**丢闭合标签不报 HTML 错**，
  而是把后面的 HTML 注释和 `<script src=…>` **吃进 JS** → 整段抛 SyntaxError、**静默失效**
  （页面看着正常、交互全死、构建期零报错）。这是最阴的一类 bug。
- 方案: 补回 `</script>`；在 `test/agentic.test.mjs` 新增守卫，扫**全部 49 页**断言 `<script>` 与 `</script>` 数量相等。
- 验证: 配平检查 10/10 ✅；`npm test` 全绿
- 回滚方案: 无（纯修 bug）
- 结论: ✅ 通过。另注：`tools/check-inline-js.py` 是同类检查但**不在 `npm test` 里**，改内联脚本后需手动跑一次。

## 2026-09-11 修复「6 个测试长期假绿」（测试读的是构建产物）
- 改动人: agent
- 改动文件: `test/{admin-gate,admin-orders-users-tools,ai-analyst,p1-billing,p2-content,p3-tickets}.test.mjs`
  + 新增 `test/build-sync.test.mjs` + `package.json`（`npm test` 加入新守卫）
- 问题: 上述 6 个测试原本 `import` 的是**构建产物** `site/_worker.js`。源码改了、产物没重建时，
  断言对着**旧产物**继续通过 —— 即"假绿"。实例：`billing.mjs` 已把 `success_url` 改成带 `?checkout=done`
  （前端 `upgrade.html:137` 靠它启动"付款确认中"轮询），产物没重建，`p1-billing` 就这么"通过"了很久，
  直到手动重建产物才暴露（测试数 150 → 149）。
- 方案: 6 个测试全部改读 **`worker-src/worker.mjs` 源码**（Node 可直接 import，行为与产物等价）。
  `test/diff-worker.mjs` **故意**比产物（老单文件 worker vs 新模块化产物），**不改**；
  `test/smoke-worker.mjs` 保留测产物（职责就是 bundle 冒烟）。
- 验证: 新增 `test/build-sync.test.mjs` —— 用 esbuild `write:false` 内存重建，与磁盘产物**逐字节比对**，
  不同步就红。**已验证它不是摆设**（故意篡改产物 → 红；重建 → 绿）。测试数 **151/151** 通过。
- 回滚方案: 恢复为 import 产物（不建议，等于恢复假绿）
- 结论: ✅ 通过。**以后新增读 worker 的测试一律 import 源码，不要 import `site/_worker.js`。**

## 2026-09-11 修复自检脚本吞掉网络错误真实原因
- 改动人: agent
- 改动文件: `tools/creem-live-check.mjs`
- 问题: 用户跑 `npm run live-check` 得到 `[FAIL] report-checkout 请求失败  fetch failed`，无从下手。
  实际原因是**本机出网**：Node 的 fetch 只在 `e.message` 写 "fetch failed"，真实原因藏在 **`e.cause`**；
  且**非本站故障** —— 部署其实是成功的（线上路由已由 404 变 400）。
- 方案: ①**代理自愈**：在任何请求前清掉 6 个代理环境变量
  （`HTTP_PROXY/HTTPS_PROXY/ALL_PROXY` 及小写 —— **Windows 环境变量名不区分大小写**，
  `process.env['http_proxy']` 会返回大写那个的值），逃生舱 `LIVECHECK_USE_ENV_PROXY=1`；
  ②新增 `why(e)` 打印 `e.cause.code`、`netHint(e)` 按错误码给不同指引、`curlFallback()` 给不依赖 Node 的备份命令；
  ③结论区新增「其中 N 条是本机出网失败，线上真实状态未知」提示。
- 验证: 正常场景 11/11 绿；`Node 24 + HTTPS_PROXY=http://127.0.0.1:7897`（修复前必红）现在也 11/11 绿；
  `SITE_URL=http://127.0.0.1:9999` 强制 ECONNREFUSED → 正确打印 `[ECONNREFUSED]` + 指引 + curl 备份。
- 回滚方案: 无（纯增强）
- 结论: ✅ 通过。**根因记录：Node 24 会自动读 `HTTPS_PROXY` 让 fetch 走它，Node 22 不读；这台机器的代理端口角色还会来回反转，一律实测为准。**
